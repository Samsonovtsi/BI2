# BI2 — три раздела и единая карта требований
Статус: первая итерация интерфейса, 27.10.2026. Этот документ не подменяет исходное ТЗ и формулы Google Sheets.

## Верхний уровень навигации
В интерфейсе ровно три верхнеуровневых раздела:
1. **Карта онлайн** — ЭР, АКК, ДомКлик, обзор, аналитика и тепловая карта, карточки городов, банки и комиссии, НС, светофор городов, планы, отчёты, Космос, отклонения, источники.
2. **Светофор риелторов** — отдельное место для рейтинга сотрудников ЭР/АКК/НС по ТЗ «Светофор допсервисов». Пока нет сопоставленных первичных сделок сотрудников, экран показывает явное состояние «нет данных» вместо имитации статистики.
3. **Калькулятор АКК** — имеющийся расчёт по группам чеков, отдельные подразделы «По сделкам» и «Тарифы и удержания», требующие дальнейшей интеграции источников.

Существующие методы и страницы не удалены. Переименован и перенесён прежний **светофор городов**: он не является светофором сотрудников.

## 1. Карта онлайн
Контрольные листы:
- [Свод ЭР+АКК (копия) (копия)](https://docs.google.com/spreadsheets/d/1dkA1CUyrYh5qd2MmeLJ2qzXcqMTHVGDIX0S8mZQ7JMs/edit?gid=559499648)
- [Свод по городу NEW](https://docs.google.com/spreadsheets/d/1dkA1CUyrYh5qd2MmeLJ2qzXcqMTHVGDIX0S8mZQ7JMs/edit?gid=943090579)

Город, ФиФ, категория вала и период сохранены. РОП/МОП отображены как **недоступные до подключения оргструктуры**; никакой фиктивной фильтрации не происходит.

Сравнение: лучшая практика и худшая практика образуют серую область, выбранный город — красная линия, вся сеть — отдельная линия. Должны выполняться фильтры группы сравнения и минимальной базы. Для ДомКлик меньшая доля конкурента считается лучше. Существующий график `renderCompare` оставлен.

В тепловой карте есть два режима:
- **Проникновение, %**: исходные проценты не изменяются, предварительная раскраска <30% красный, 30–59.9% жёлтый, ≥60% зелёный; для ДомКлик направление обратное.
- **Выполнение плана города, %**: цвет по доле `факт проникновения / план проникновения × 100%`. Красный <80%, жёлтый 80–99.9%, зелёный ≥100% — **предварительные пороги**. Отсутствие или нулевой план — нейтральный серый цвет, не 0% достижения. Планы берутся из `GET /api/plans` только для той же метрики/месяца и `method=summary` (исходный свод); для NEW нельзя использовать план исходной методики. Число в ячейке по-прежнему показывает исходный % проникновения, подсказка — процент выполнения плана.
- Сортировка по грейду вала использует явную последовательность A++ → A+ → A → B → C → D → E; при равном грейде — по проникновению.

Цветовые пороги необходимо утвердить владельцем показателей; не смешивать *грейд вала*, *процент проникновения* и *процент выполнения цели*. В следующей итерации добавить редактируемый каталог порогов с ролями и журналом.

Для **среднего дохода с одной сделки АКК** необходимо связать доход с уникальными `deal_id`. Текущий средний банковский доход на операцию не обозначать как средний на уникальную сделку.

## 2. Светофор риелторов
Источник: [ТЗ Светофор допсервисов](https://docs.google.com/document/d/1yQlVdJuMKvRsxfkYh9VZrvpSheFHK6pbg4Pn_getSu0/edit), [существующий образец](https://ecosystem.etagi.com/trafficLight).

Требуемые поля источника:
- `deal_id`, `client_id`, `employee_id`, `city_id`, признак доступности ЭР/АКК/НС, финансовая дата, статус;
- `service_id`, `deal_id`, тип продукта, банк, ответственный, даты оформления и отмены;
- `commission_id`, `service_id`, `employee_id`, сумма, дата признания, удержания, возвраты;
- `employee_id`, ФИО, дата начала работы, партнёр/старший партнёр, `rop_id`, `mop_id`, `spn_id`, город и история связей `valid_from`/`valid_to`;
- связь с CRM по **стабильным внутренним ID**, не по совпадению ФИО клиента.

Цель: уникальные сделки с одним или несколькими выбранными продуктами (ЭР, АКК, НС), без двойного подсчёта совпадающих сделок; выбранные продукты независимы. Рейтинг, поиск сотрудника/партнёра/старшего партнёра, месяц/год/всё время, пагинация, сортировки, комиссионные рекорды за 1 месяц, персональный план и прогресс.

**Конфликт исходного ТЗ**: написана формула `все сделки / сделки с доппродуктами`, ниже сказано, что числитель — сделки с доппродуктами. Предлагаемый вариант — `уникальные подходящие сделки с выбранными доппродуктами / все уникальные подходящие сделки сотрудника × 100%`. Нужны бизнес-подтверждения области подходящих сделок для разных продуктов и условий договоров.

Переход от города к РОП → МОП → СПН → клиенту не может появиться из агрегированного городского свода. Нужны ID, разграничение ролей и история иерархии. Клиентские строки должны быть скрыты для пользователей без прав.

## 3. Калькулятор АКК
Источник: [Калькулятор Голендухина](https://docs.google.com/spreadsheets/d/1es-6KsSYuDKYCfusMtFwFQCqQWnI7-WdhnOO-LTNkz8/edit?gid=1180972308), [Детализация по сделкам](https://docs.google.com/spreadsheets/d/1es-6KsSYuDKYCfusMtFwFQCqQWnI7-WdhnOO-LTNkz8/edit?gid=489943861). Каталоги: [Матрицы выплат](https://docs.google.com/spreadsheets/d/1es-6KsSYuDKYCfusMtFwFQCqQWnI7-WdhnOO-LTNkz8/edit?gid=802839738) и [Базовые % города](https://docs.google.com/spreadsheets/d/1es-6KsSYuDKYCfusMtFwFQCqQWnI7-WdhnOO-LTNkz8/edit?gid=2002467773).

Первая итерация сохраняет действующий агрегатный калькулятор по диапазонам чеков, готовые значения КВ из исходного листа, фактический доход и потенциальный прирост. Для расчёта на сделке нужно переносить связанные события и банковские тарифы по времени, минимумы/максимумы суммы, сроки и ограничения. «Лучший» — максимум **допустимой** чистой КВ города, после удержаний ЦО, а не максимум любого числа в таблице.

Тарифная модель: уникальный `tariff_id`, банк, город/группа, продукт, правила суммы и срока, дата начала и окончания, КВ банка, доля города и удержание ЦО, версия, автор изменений. Любое изменение должно проходить авторизованную форму с аудитом, без переписывания закрытого месяца. Пока эти функции **не введены в эксплуатацию** и редактор тарифов не активирован.

## Что обязательно проверить перед выпуском
1. `npm test` и проверка статического синтаксиса всех клиентских скриптов.
2. Три верхнеуровневые навигационные кнопки и возврат между всеми подразделами.
3. Данные Карты, отчётов, Космос и калькулятора до и после изменения идентичны при одинаковых фильтрах.
4. Красная линия выбранного города и серый диапазон двух эталонов отображаются на графике.
5. Тепловая карта с планом/без плана, со значением плана 0 и для ДомКлик; сортировка грейдов.
6. Мобильная верстка и доступность клавиатуры.
7. Ограничение доступа перед подключением персональных и клиентских данных.
8. Проверить деплой: GitHub-коммит не равен обновлению рабочего хостинга.
